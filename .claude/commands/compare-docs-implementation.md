# ドキュメント実装比較

ADR・設計ドキュメントと現状の実装との乖離を洗い出し、修正方針を提案するワークフロー。

## 比較対象ドキュメント

以下のドキュメントカテゴリを順次調査する：

1. **ADR** (`docs/adr/*.md`)
   - アーキテクチャ決定記録
   - 技術選定の根拠と制約

2. **Clean Architecture設計** (`docs/design/clean-architecture/`)
   - レイヤー構造の定義
   - エンティティ設計

3. **機能設計** (`docs/design/pages/`, `docs/design/src/`)
   - 画面・機能単位の設計
   - クラス設計、シーケンス

4. **コーディング標準** (`docs/coding-standards/`)
   - 実装規約
   - テスト規約

## 実行手順

### Step 1: ドキュメント一覧の取得

```
docs/adr/*.md
docs/design/**/*.md
docs/coding-standards/**/*.md
```

上記パターンでドキュメントを列挙し、比較作業用のTODOタスクを作成する。

### Step 2: 各ドキュメントの比較

ドキュメントごとに以下を実行：

1. **ドキュメント内容の読み取り**
   - 記載されているルール・設計・制約を抽出

2. **対応する実装の調査**
   - Grep/Globで関連コードを検索
   - 実装の現状を把握

3. **乖離の特定**
   - ドキュメントに書かれているが実装されていない
   - 実装されているがドキュメントに記載がない
   - ドキュメントと実装で内容が異なる

### Step 3: 乖離リストの作成

以下の形式で乖離を記録：

```markdown
## 乖離リスト

### [ドキュメントパス]

| 項目 | ドキュメント | 実装 | 乖離タイプ | 修正方針 |
|------|------------|------|-----------|---------|
| ... | ... | ... | 未実装/未記載/不一致 | ドキュメント修正/実装修正/要検討 |
```

### Step 4: 修正方針の判断基準

**ドキュメントを修正すべき場合：**
- 実装が正しく、ドキュメントが古い
- 実装の方が合理的な設計である
- ADRで決定後に正当な理由で変更された

**実装を修正すべき場合：**
- ドキュメントの設計意図が正しい
- 実装がルールに違反している
- バグや技術的負債として認識される

**要検討の場合：**
- どちらが正しいか判断できない
- 両方に問題がある可能性
- ユーザーへの確認が必要

### Step 5: 結果報告

乖離リストと修正方針をユーザーに報告し、次のアクションを確認する。

## 出力例

```markdown
## 比較結果サマリー

- 比較したドキュメント数: X
- 乖離が見つかったドキュメント数: Y
- 乖離総数: Z
  - ドキュメント修正推奨: A件
  - 実装修正推奨: B件
  - 要検討: C件

## 詳細

### docs/adr/001-clean-architecture-with-presenter-pattern.md

| 項目 | ドキュメント | 実装 | 乖離タイプ | 修正方針 |
|------|------------|------|-----------|---------|
| Presenterの配置 | interface-adapters | application | 不一致 | 実装修正 |

...
```

## 注意事項

- 全ドキュメントを一度に比較すると時間がかかるため、カテゴリごとに分割して実行可能
- ユーザーが特定のドキュメントを指定した場合はそれのみを比較
- 乖離が多い場合は優先度をつけて報告
