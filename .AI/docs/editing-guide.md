# docs/ 配下のドキュメント作成・編集ガイドライン

## 基本原則

`docs/` 配下のドキュメントを作成・編集する際は、以下の2種類のガイドラインに従うこと：

1. **全ドキュメント共通のガイドライン**: `docs-rules/` 直下に定められているルール（`docs-rules/common/index.md` 等）
2. **カテゴリ固有のガイドライン**: 作成・編集するディレクトリに対応する `docs-rules/` 以下のディレクトリに定められているルール（例: `docs/coding-standards/` → `docs-rules/coding-standards.md` および `docs-rules/coding-standards/`）

### ガイドラインの階層

ガイドラインは階層構造になっており、**該当レベルのガイドラインとすべての上位ガイドライン**に準拠する必要がある。

例: `docs/design/pages/rule-list/features/delete-rule/integration-test-strategy.md` を作成する場合

1. `docs-rules/common/index.md` （共通ルール）
2. `docs-rules/design/` 配下の該当ガイドライン（例: `06-integration-test-strategy.md`）

## チェックリスト

1. [ ] **共通ルールを確認**: `docs-rules/common/index.md`（マークダウン記法、文体など全ドキュメント共通）
2. [ ] **該当カテゴリのルールを確認**:
   - カテゴリ概要: `docs-rules/[category].md`（例: `user-stories.md`、`design.md`）
   - 詳細ルール: `docs-rules/[category]/` ディレクトリ内
3. [ ] **必須セクションを確認**: 該当ガイドライン内の「必須セクション」表を参照
   - 例: `docs-rules/design/06-integration-test-strategy.md` の「必須セクション」セクション
4. [ ] **配置ルールを確認**: ファイルの配置場所がガイドラインに準拠していることを確認
5. [ ] ドキュメントを作成・編集
6. [ ] **影響ドキュメントを確認・更新**: ガイドラインの「影響ドキュメント」セクションに記載されたファイルも更新

## リンク作成時のチェック

ドキュメント内で他のファイルへのリンクを作成する場合は、以下を確認すること：

1. [ ] **リンク先ファイルの存在確認**: 相対パスでリンクを追加する前に、対象ファイルが実在することを確認
   ```bash
   # 例: ADR-007の実際のファイル名を確認
   ls docs/adr/007-*.md
   ```
2. [ ] **ADR参照時の正式名確認**: ADRを参照する場合は `docs/adr/` 配下の実際のファイル名を使用（推測しない）
3. [ ] **相対パスの検証**: 作成したリンクが正しく解決されることを確認
4. [ ] **ディレクトリ/ファイル名の混同防止**: ディレクトリ名を単一ファイルとして参照していないか確認

### ディレクトリ/ファイル名混同の例

```markdown
❌ 誤り: ディレクトリ名をファイルとして参照
[common-rule.md](../coding-standards/tests/common-rule.md)
# common-rule.md は存在しない。common-rule/ はディレクトリ

✅ 正しい: ディレクトリ内の具体的なファイルを参照
[mock-file-placement.md](../coding-standards/tests/common-rule/mock-file-placement.md)
# または index.md を参照
[common-rule/index.md](../coding-standards/tests/common-rule/index.md)
```

**確認方法**:
```bash
# ディレクトリかファイルかを確認
ls -la docs/coding-standards/tests/common-rule
# ディレクトリの場合、内部のファイル一覧を確認
ls docs/coding-standards/tests/common-rule/
```

### 相対パスの階層数検証

深い階層のドキュメントから他のファイルを参照する場合、`../` の数を数え間違えやすい。

**検証手順**:

1. ソースファイルのディレクトリに移動
2. 相対パスが正しく解決されるか `ls` で確認

```bash
# 例: docs/design/src/application/usecases/rule/UpdateRewriteRuleUseCase/execute.md から
# docs/coding-standards/tests/common-rule/mock-file-placement.md を参照する場合

cd docs/design/src/application/usecases/rule/UpdateRewriteRuleUseCase
ls ../../../../../../coding-standards/tests/common-rule/mock-file-placement.md
# ファイルが表示されればOK、エラーなら階層数が間違っている
```

**よくある間違い**:
- ファイル名を1階層としてカウントしてしまう（ファイルは階層に含まない）
- 目視で `../` を数える際のオフバイワンエラー

**正しいカウント方法**:
```
docs/design/src/application/usecases/rule/UpdateRewriteRuleUseCase/execute.md
     ↑      ↑   ↑           ↑        ↑    ↑                       ← ファイルは含まない
     1      2   3           4        5    6  ← docs/ 配下のディレクトリ数 = ../ の数
```

**注意**: `docs/` 自体はカウントに含めない。上記の例では `docs/` に到達するために 6 個の `../` が必要。
`docs-rules/`（リポジトリルート）に到達するには 7 個の `../` が必要。

## 設計ドキュメント変更時の追加チェック

設計ドキュメント（`docs/design/`）を変更する場合は、以下も確認すること：

1. [ ] **関連値の一貫性確認**: プロパティ名やDTO定義を変更した場合、`grep -r "変更前の値" docs/design/` で関連ファイルを検索
2. [ ] **同一PR内の整合性**: 変更したドキュメントを参照している他のドキュメントとの矛盾がないこと

## 実装変更時の設計ドキュメント同期

ソースコード（CSS、TypeScript等）を変更した場合、対応する設計ドキュメントも同期させること。

### CSSを変更した場合

1. [ ] **UI設計書との同期**: 対応する `docs/design/` 配下のUI設計書が存在する場合、CSS変更内容を反映
   - レスポンシブ対応（`@media`クエリ）を追加・変更した場合 → 設計書の「レスポンシブ対応」セクションを更新
   - 列幅・レイアウトを変更した場合 → 設計書の「列構成」「列幅の実装」セクションを更新
   - 新しいスタイルプロパティを追加した場合 → 設計書の該当セクションを更新

2. [ ] **影響範囲の特定**:
   ```bash
   # 変更したコンポーネントに対応する設計ドキュメントを検索
   grep -r "RulesTable" docs/design/
   ```

### 同期漏れを防ぐためのチェックポイント

- **CSS変更時**: `docs/design/` 配下に対応するUI設計書（`ui.md`等）があるか確認
- **コンポーネント変更時**: 設計書の「コンポーネント構成」セクションと一致しているか確認
- **レスポンシブ対応追加時**: 設計書の「レスポンシブ対応」セクションにコード例が含まれている場合、追加したCSSも記載

## コーディング標準と実装の一貫性チェック

コーディング標準（`docs/coding-standards/`）を新規作成・更新した場合、同一PRで関連する実装も修正する際は：

1. [ ] **ガイドラインに記載したパターンと実装が一致しているか確認**
2. [ ] **特にコード例を含むガイドラインでは、実装がその例に準拠しているか再確認**

## テンプレートと例の一貫性

テンプレート定義と使用例を同一ドキュメントに記載する場合は、**用語・表記を完全に一致させること**。

### 規約

- テンプレートで定義した選択肢・記載形式と、例で使用する表記を一致させる
- 表記ゆれ（`vi.fn()直接` vs `vi.fn()で直接モック`）を避ける
- テンプレートを更新した場合、同一ドキュメント内のすべての例も更新する

### チェックリスト

テンプレートを含むドキュメント（`docs-rules/`配下等）を編集する際は以下を確認：

1. [ ] **テンプレートの選択肢と例の表記が一致しているか**
2. [ ] **同一ドキュメント内で同じ概念に異なる表現を使っていないか**
   ```bash
   # 例: vi.fn()関連の表記ゆれを検索
   grep -n "vi\.fn()" docs-rules/design/05-test-strategy.md
   ```

## 判断基準を記載する際のルール

ドキュメントで「どちらを選ぶか」の判断基準を記載する場合は、以下を遵守すること：

### 具体例の対比原則（必須）

抽象的な基準だけでなく、**異なる結果になる具体例を最低2つ以上**示すこと。

```markdown
❌ 悪い例：抽象的な基準のみ
| 条件 | 配置先 |
|------|--------|
| 複数機能で使用 | グローバル |
| 単一機能で使用 | 機能固有 |

✅ 良い例：具体例で対比を示す
| 定数名 | 配置先 | 理由 |
|--------|--------|------|
| `DEFAULT_TIMEOUT` | グローバル | 全機能で共通使用される汎用タイムアウト |
| `CONFIRM_DIALOG_TIMEOUT` | 機能固有 | 削除確認ダイアログ固有、削除機能でのみ使用 |
```

### 理由の明示

「AはXだからY」「BはXではないからZ」という形式で、なぜその判断になるのかを明示する。

### チェックリスト

判断基準を記載するドキュメントを作成・編集する際は以下を確認：

1. [ ] **抽象的な基準表**が存在するか
2. [ ] **具体例の対比表**が存在するか（最低2例、異なる結果になるもの）
3. [ ] 各具体例に**理由**が記載されているか
