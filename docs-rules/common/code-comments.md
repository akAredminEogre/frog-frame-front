# コード内コメントの記述原則

コード内のコメント（JSDoc、インラインコメント等）にも以下の原則を適用する。

## 原則: 専門用語・抽象的な表現を避け、具体的に記述する

コメントは初めてコードを読む人が理解できる表現で記述すること。

| 避けるべき表現 | 推奨する表現 |
|---------------|-------------|
| カスケード障害を防ぐ | 他のテストケースへの影響を防ぐ |
| パフォーマンス向上のため | 不要な再レンダリングを防ぐため |
| 安全性のため | null参照エラーを防ぐため |
| 堅牢性を高める | エラー時にも正常に動作させる |

## 「なぜ」を具体的に書く

```typescript
// ❌ 悪い例: 「カスケード障害」は専門用語で意味が不明確
// カスケード障害を防ぐため早期リターン
if (!container) return;

// ✅ 良い例: 具体的な影響を記述
// setup()が呼ばれていない場合は何もせず早期リターン（他のテストケースへの影響を防ぐため）
if (!container) return;
```

## 実装詳細をコメントに含めない

将来変更される可能性のある実装詳細（具体的な値、内部形式など）をコメントに記載しない。

```typescript
// ❌ 悪い例: 実装詳細（":r0:"形式）に言及
// useIdは":r0:"のような形式のIDを生成するため、IDが存在することを確認
expect(title?.id).toBeTruthy();

// ✅ 良い例: 実装詳細を抽象化
// useIdで動的に生成されるため、IDの形式は実装依存。プレフィックス部分のみ検証する
expect(title?.id).toBeTruthy();
```

**なぜ避けるべきか**:
- 実装詳細は将来変更される可能性がある
- コメントがコードと乖離すると誤解を招く
- 「何をしているか」ではなく「なぜそうしているか」を書く

## 能力ではなく実際の動作を記述する

コメントは「何ができるか」ではなく「何をするか」を記述する。

```typescript
// ❌ 悪い例: 能力を記述（実際の動作が不明確）
// プレフィックスは確認可能
expect(id).toContain('dialog-');

// ✅ 良い例: 実際の動作を記述
// プレフィックス部分のみ検証する
expect(id).toContain('dialog-');
```

| 避けるべき（能力） | 推奨（実際の動作） |
|------------------|------------------|
| 〜は確認**可能** | 〜を**検証する** |
| 〜に対応**可能** | 〜を**処理する** |
| エラーハンドリング**可能** | エラーを**キャッチしてログ出力する** |

## チェックリスト

コメントを書く際は、以下を確認すること:

- [ ] 初めてコードを読む人が理解できる表現か
- [ ] 専門用語や業界ジャーゴンを使っていないか
- [ ] 「なぜ」が具体的に説明されているか
- [ ] 将来変更される可能性のある実装詳細（具体的な値、形式など）を含んでいないか
- [ ] 能力（〜可能）ではなく実際の動作（〜する）を記述しているか
