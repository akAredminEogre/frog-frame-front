# 07-e2e-test-strategy.md ルール

E2Eテストの設計意図と網羅性を可視化するドキュメント。

## 目的

- ユーザー視点での機能動作を検証する設計を明文化
- UIからDB永続化までのエンドツーエンドのフローを可視化
- テスト環境（Playwright、ローカルHTTPサーバー等）の構成を明確化
- ユーザーストーリーとの対応関係を定義

## 配置

E2Eテスト戦略書は、featureの `00-overview.md` と同じディレクトリに配置する。

```plaintext
docs/design/pages/{page-name}/features/{feature-name}/
├── 00-overview.md
├── integration-test-strategy.md
└── e2e-test-strategy.md    # ← ここに配置
```

## 必須セクション

| セクション | 必須 | 説明 |
|-----------|------|------|
| 目的 | ○ | E2Eテストで検証する内容を簡潔に記述 |
| テストスコープ | ○ | 対象ページ、操作フロー、検証ポイント |
| テスト分類 | ○ | テストケースを観点ごとに分類 |
| ユーザーストーリートレーサビリティ | ○ | ユーザーストーリーとの対応 |
| 網羅性チェック | ○ | 過不足を確認するチェックリスト |
| テストファイル構成 | ○ | 実際のテストファイルとの対応 |
| テスト環境 | ○ | テストページ、ローカルHTTPサーバー等 |

**注意**: ヘルパー関数のシグネチャ等の実装詳細は記載しない。テストコードを読めば分かる内容は戦略書に含めない。

### テスト環境セクションの記述ルール

- **Playwright設定は記載しない**: ブラウザ種別、タイムアウト等の標準的なPlaywright設定は記載不要
- **記載すべき内容**: テストページ、ローカルHTTPサーバー等のテスト固有の環境情報のみ
- **例外**: 標準設定から逸脱する場合のみPlaywright設定を記載する

## テストスコープの定義

### 対象フローの記述

ユーザー操作の流れをステップで示す:

```markdown
### 対象フロー

1. ユーザーがルール一覧ページを開く
2. トグルスイッチをクリック
3. ルールの有効/無効が切り替わる
4. ページをリロードしても状態が維持される

### 対象ページ

| ページ | URL | 役割 |
|-------|-----|------|
| ルール一覧 | `chrome-extension://{id}/rules.html` | トグル操作 |
| ポップアップ | `chrome-extension://{id}/popup.html` | ルール作成 |
| テストページ | `http://localhost:8080/test.html` | DOM置換検証 |
```

### 検証ポイント

E2Eテスト特有の検証観点:

| 観点 | 説明 | 例 |
|------|------|-----|
| UI状態変化 | 操作後のUI表示 | トグルがON→OFF |
| DB永続化 | リロード後も状態維持 | ページリロードで確認 |
| コンソールエラー | エラーが発生しないこと | `console.error` 監視 |
| ダイアログ表示 | アラート/確認ダイアログ | 保存完了メッセージ |

## テスト分類の観点

00-overview.mdの機能要件を踏まえて分類する。

**テスト分類ごとにファイルを分割する**。各テスト分類に対応するテストファイルを作成し、テストの責務を明確にする。

```markdown
### 1. 正常操作フロー - 状態切り替えとDB永続化

[この観点でテストする理由]

| 分類 | テストケース | 根拠 |
|------|-------------|------|
| true → false | 有効なルールを無効に切り替え + リロード確認 | 基本パターン + DB永続化 |
| false → true | 無効なルールを有効に切り替え + リロード確認 | 基本パターン + DB永続化 |

**対応テスト**: `normal-cases.spec.ts`

※ DB永続化の検証は各テストケース内でページリロード後の状態確認として実施する。
  状態切り替えと永続化は一連のフローとして検証するため、別ファイルには分割しない。
```

### テストファイル構成

テスト分類ごとにファイルを分割して配置する:

```plaintext
tests/e2e/pages/{page-name}/features/{feature-name}/
├── helpers.ts                  # 共通ヘルパー関数
├── normal-cases.spec.ts        # 正常操作フロー（DB永続化含む）
├── data-independence.spec.ts   # 複数データ独立性
├── concurrency.spec.ts         # 競合防止
└── error-cases.spec.ts         # エラー系（該当する場合）
```

### テストファイルリファクタリング時の同期

テストファイルを分割・統合した場合、対応するテスト戦略書を必ず更新すること。

**チェックリスト**:
- [ ] テスト戦略書の「対応テスト」欄が実際のファイル構成と一致しているか
- [ ] 分割した場合は複数ファイルを列挙しているか
- [ ] テストファイル構成セクションが最新のディレクトリ構造を反映しているか

## 記述ルール

### ユーザー操作の記述

ユーザー視点での操作を具体的に記述:

```markdown
### 対象フロー

1. ユーザーがポップアップを開く
2. 置換前/置換後の文字列を入力
3. 「保存」ボタンをクリック
4. 「保存して適用しました！」ダイアログが表示される
5. ルール一覧ページで保存されたルールが表示される
```

## 結合テストとの関係

| 結合テスト | E2Eテスト |
|-----------|----------|
| Factory→Controller→UseCase→DB | UI→拡張機能全体→DB |
| モック: Chrome API | モック: なし（実環境） |
| 高速（Vitest） | 低速（実ブラウザ） |
| 詳細なエラー検出 | ユーザー体験の検証 |

両方のテストを組み合わせることで、信頼性を担保する:

1. **結合テスト**: ロジックの正確性を高速に検証
2. **E2Eテスト**: 実環境でのユーザー体験を検証
