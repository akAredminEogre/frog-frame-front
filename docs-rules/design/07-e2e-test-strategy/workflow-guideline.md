# E2Eテスト戦略書 ワークフローガイドライン

E2Eテスト戦略書を作成・編集する際の動作ガイドライン。

## 新規作成時のワークフロー

1. [format-guideline.md](./format-guideline.md) の必須セクションを確認
2. 00-overview.md の機能要件を確認
3. テスト分類を決定し、各分類に対応するテストファイル名を決定
4. 戦略書を作成

## テストファイルリファクタリング時の同期

テストファイルを分割・統合した場合、対応するテスト戦略書を必ず更新すること。

> **Note**: ドキュメントファイル自体のリファクタリング（ファイル名変更・分割・統合）を行う場合は、[ドキュメントリファクタリング時の同期ルール](../../common/document-consistency/document-refactoring.md)に従うこと。

**チェックリスト**:
- [ ] テスト戦略書の「対応テスト」欄が実際のファイル構成と一致しているか
- [ ] 分割した場合は複数ファイルを列挙しているか
- [ ] テストファイル構成セクションが最新のディレクトリ構造を反映しているか

## テストケース追加時の同期

テストケースを追加した場合、対応するテスト戦略書のテスト分類セクションを必ず更新すること。

**重要**: テスト戦略書に記載のないテストケースは追加しない。追加する場合は先に戦略書を更新する。

**チェックリスト**:
- [ ] 実装したテストケース数と戦略書の定義数が一致しているか
- [ ] テストケースの説明文（describe/test内の文字列）が戦略書の記載と一致しているか
- [ ] 新しいテストケースには「根拠」欄でなぜそのテストが必要かを明記しているか

**手順**:
1. テストケースを追加したい場合、まずテスト戦略書のテスト分類表に行を追加
2. テストコードを実装
3. 実装完了後、戦略書の定義と実装が一致していることを確認

## トレーサビリティ表の更新

ユーザーストーリートレーサビリティ表は、受け入れ条件とテスト実装の対応を示す重要な成果物である。

**重要**: トレーサビリティ表の「テストケース」欄は、**実際のE2Eテストが検証する内容**を正確に記述すること。受け入れ条件の文言をそのままコピーしない。

**理由**: 受け入れ条件の実現方法がE2Eで直接検証できない場合、代替の検証方法を採用することがある。この場合、トレーサビリティ表にはE2Eで実際に検証する内容を記載しないと、テスト実装との齟齬が生じる。

**例**:
- ❌ `AC-8: 重複削除防止 | 削除処理中はボタン無効化`（ACの文言そのまま）
- ✅ `AC-8: 重複削除防止 | 確認ダイアログ表示中の再クリックでもダイアログは1つのまま`（E2Eでの実際の検証内容）

**チェックリスト**:
- [ ] トレーサビリティ表の「テストケース」欄がE2Eテストの実際の検証内容を反映しているか
- [ ] E2E検証困難な項目は結合テストへのパスを記載しているか
- [ ] テスト実装後にトレーサビリティ表を再確認したか
