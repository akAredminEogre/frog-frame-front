# テスト命名規則

E2Eテストのテスト名（`test()`の第1引数）に関するルール。

## 基本原則：検証内容を正確に記述する

テスト名は**実際のアサーションが検証する内容**を正確に記述すること。意図や期待する振る舞いではなく、テストコードが検証している具体的な事実を記述する。

### NG例：意図を記述

```typescript
// ❌ 「操作可能」と記述しているが、実際はdisabled属性のみ検証
test('削除処理中も他のルールの編集ボタンは操作可能', async () => {
  // ...
  await expect(editButton).not.toBeDisabled();  // 属性チェックのみ
});
```

### OK例：検証内容を記述

```typescript
// ✅ 実際の検証内容（disabled属性）を明記
test('削除確認ダイアログ表示中も他のルールの編集ボタンはdisabledにならない', async () => {
  // ...
  await expect(editButton).not.toBeDisabled();
});
```

## 命名の判断基準

| アサーション | 適切なテスト名の例 |
|-------------|------------------|
| `toBeDisabled()` / `not.toBeDisabled()` | 「〜はdisabledになる」「〜はdisabledにならない」 |
| `toBeVisible()` / `not.toBeVisible()` | 「〜が表示される」「〜が非表示になる」 |
| `toHaveCount(n)` | 「〜がn件表示される」「〜は1つだけ表示される」 |
| `toHaveText()` | 「〜に"xxx"と表示される」 |
| `click()` + URL確認 | 「〜をクリックすると〜に遷移する」 |

## 「操作可能」の注意点

「操作可能」「クリック可能」という表現は曖昧で、以下の異なる検証を含みうる：

1. **disabled属性が設定されていない** → `not.toBeDisabled()`
2. **実際にクリックできる**（オーバーレイ等でブロックされていない）→ `click()` + 結果確認
3. **クリック後に期待した動作が起こる** → `click()` + 遷移/状態変化確認

テスト名は、上記のどれを検証しているかを明確に記述すること。

## 状態の明示

テスト名には**いつ**（どの状態で）検証しているかも明記すること。

### NG例：状態が曖昧

```typescript
// ❌ 「削除処理中」は曖昧（確認ダイアログ表示中？API呼び出し中？）
test('削除処理中も編集ボタンはdisabledにならない', ...);
```

### OK例：状態が明確

```typescript
// ✅ 「確認ダイアログ表示中」と具体的に記述
test('削除確認ダイアログ表示中も編集ボタンはdisabledにならない', ...);
```

## チェックリスト

テスト名を決める際は以下を確認すること：

- [ ] テスト名がアサーションの検証内容と一致しているか
- [ ] 曖昧な表現（「操作可能」「動作する」等）を避けているか
- [ ] 検証タイミング（状態）が明確か
- [ ] テスト戦略書の記載と一致しているか
