# コーディング規約ドキュメントの記述ルール

## 概要

`docs/coding-standards/` 配下に配置するコーディング規約ドキュメントの記述ルール。

**前提**: [common/index.md](./common/index.md) の一般原則に加え、コーディング規約固有のルールを以下に定義する。

## 記述ルール

### 実装例は記述しない

コーディング規約には**実装例を記述しない**。

**理由**:
- 実装例はコードベース内の実際のコードを参照すべき
- ドキュメントとコードの二重管理を避ける
- 規約の本質（何をすべきか/すべきでないか）に集中する

### 記述すべき内容

- 命名規則
- 型の使い分け方針
- 禁止事項と許可事項
- eslint-ruleセクション

### eslint-ruleセクション

`## eslint-rule` セクションを設け、**各規約ごとに** ESLintルールの有無を明示する。

- ESLintルールがある場合: ルールファイルへの**リンク**を記述（リポジトリルートからの相対パス）
  - 実在する例: [host-frontend-root/frontend-src-root/eslint-rules/react.js](../../host-frontend-root/frontend-src-root/eslint-rules/react.js)
  - 実装コードの掲載は不要（リンク先で確認できるため）
- ESLint化できない場合: その旨を記述
  - ESLint化できない場合は、無理に空のeslint-rule.jsのファイルを作成しないこと

### 記述すべきでない内容

- 実装例（Good/Bad 例も含む）
- コードスニペット
- ユースケース固有の実装パターン

### 適用シナリオは記載する

[common/rule-writing-principles.md](./common/rule-writing-principles.md) の「規約・ルール記述時の原則」に従い、**適用シナリオや判断事例**は1-2個記載すること。

**「実装例」と「適用シナリオ」の違い**:

| 種別 | 記載 | 説明 | 例 |
|-----|-----|-----|-----|
| 実装例 | ❌ | コードスニペット、Good/Bad例 | `const x = ...` のようなコード |
| 適用シナリオ | ✅ | いつ・どこでこの規約を適用するかの判断事例 | 「フォーカストラップが必要な場合」「ESCキーで閉じるべき場合」 |

**良い適用シナリオの例**:
- 「ユーザーが入力中に背景コンテンツへ移動すると操作が中断されるため、フォーカストラップが必要」
- 「確認ダイアログでは、誤操作防止のためESCキーで閉じる機能を提供する」

## 新規規約追加時のルール

### 既存コードへの適用

新しいコーディング規約を追加する際は、**同一PR内で既存の違反箇所も修正すること**。

**理由**:
- 規約と実装の整合性を保つ
- 規約追加後に既存コードが違反状態で残ることを防ぐ
- レビュアーが規約の適用範囲を一目で把握できる

**手順**:
1. 新規規約をドキュメントに追記
2. `grep` や `Glob` で既存の違反箇所を検索
3. 検索結果をすべて修正
4. 同一コミットまたは同一PRで提出

**例**:
- 「flushPromisesはact()内で使用する」規約を追加 → 全てのtest-helpersで違反箇所を修正

**例外**:
- `docs/completed/` 配下の履歴ドキュメントは修正対象外（履歴の整合性を維持するため）

### 外部ライブラリに関する規約の追加

外部ライブラリ・フレームワークに関する規約を追加する際は、**公式ドキュメントで現在の推奨プラクティスを確認すること**。

**理由**:
- ライブラリのバージョンアップで推奨プラクティスが変わることがある
- 古い情報に基づいた規約は、後で修正が必要になる

**確認すべき情報**:
- 現在使用しているバージョン
- そのバージョンでの公式推奨プラクティス
- 非推奨(deprecated)になった機能がないか

**例**:
- React 18.3で`react-dom/test-utils`が非推奨に → `act`は`react`パッケージからインポートする規約に変更
