# ドキュメント共通ルール

全ドキュメント種別(ADR、設計書、テスト戦略書など)に適用される共通ルール。

## 使用言語

**ドキュメントは日本語で記述すること。**

- コード例やコマンド例は英語のまま記載可
  - コードブロック（` ``` `）内のコード
  - インラインコード（`` ` ` ``）内のコード・コマンド・ファイルパス
- 技術用語は英語表記も許容（例: Clean Architecture, Repository）

## 文体

- 文体は断定系を使うこと
  - ですます調は使わない

## 括弧について
- 全角の括弧を使わない
  - 例: （全角） → (半角)

## 原則
- コードの実装例を記入しない

## markdown記法
- Markdownのコードブロックに言語指定を行うこと
- 見出しには見出し構文（`#`, `##`, `###` など）を使用すること
  - 太字強調（`**text**`）を見出しとして使用しない
  - 見出し構文を使用することで、ドキュメント構造が明確になり、目次生成やアウトライン表示がサポートされる

## 適用待ちの箇所

規約やガイドラインを変更した際、既存のドキュメントやソースコードが新しい規約に適合していない場合がある。これらを「適用待ちの箇所」として明示的に記録する。

### 目的

- 過渡期における規約違反を可視化する
- 対応の優先度や計画を明確にする
- 新規作成時と既存修正時のルールを区別する

### 記述方法

規約を変更するドキュメントに「適用待ちの箇所」セクションを設け、以下の情報を記載する:

```markdown
## 適用待ちの箇所

### [変更内容の概要]

本規約の変更により、以下の箇所が新しい規約に適合していない:

| 対象 | 現状 | 新規約 | 備考 |
|------|------|--------|------|
| `path/to/file.ts` | 旧ディレクトリに配置 | 新ディレクトリへ移動 | 別タスクで対応 |
| `docs/design/...` | 旧フォーマット | 新フォーマットへ更新 | 優先度: 低 |

### 対応方針

- **新規作成**: 新しい規約に従う(必須)
- **既存修正**: [別タスクとして対応 / 触った際に修正 / 対応しない]
```

### 記述場所

| ドキュメント種別 | 記述場所 |
|-----------------|---------|
| ADR | 該当ADRの末尾に「適用待ちの箇所」セクションを追加 |
| コーディング規約 | 該当規約ファイルの末尾に追加 |
| 設計書ルール | `docs/docs-rules/design/` 内の該当ファイルに追加 |

### 例: ADR-004での使用

```markdown
## 適用待ちの箇所

### ドメイン層に誤って配置された Tab 関連クラス

本 ADR の決定により、以下のファイルが新しい規約に適合していない:

| 対象 | 現状 | 新規約 | 備考 |
|------|------|--------|------|
| `Tab.ts` | `src/domain/value-objects/` | `src/frameworks-and-drivers/browser/` | 別タスクで対応 |
| `Tabs.ts` | `src/domain/value-objects/` | `src/frameworks-and-drivers/browser/` | 別タスクで対応 |

### 対応方針

- **新規作成**: 新しい規約に従う(必須)
- **既存修正**: 本ユーザーストーリーのスコープ外、別途リファクタリングタスクとして実施
```

### 注意事項

- 「適用待ちの箇所」は規約違反ではなく、**計画的な移行待ち状態**である
- 新規作成時は必ず新しい規約に従うこと
- 対応完了後は該当項目を削除またはチェック済みに更新すること

## ガイドライン更新時のユーザーストーリー連携

ガイドライン(コーディング規約、テスト規約など)を更新した際、既存のコードやドキュメントとの不整合が発生する場合がある。この不整合解消は、別途ユーザーストーリーを新規作成して対応する。

### 原則

1. **ガイドラインにはユーザーストーリーへのリンクのみ表示する**
   - 不整合箇所の詳細（どのファイルが違反しているか等）はガイドラインに記述しない
   - ユーザーストーリー内で詳細を管理する

2. **ガイドライン更新PRでは、ユーザーストーリーはテンプレートのみ作成する**
   - 対象ファイル、タスク、受け入れ条件は「（別途調査）」「（別途策定）」とする
   - ユーザーストーリーの詳細策定は別途PRで対応する

3. **新規作成時は必ず新しい規約に従う**
   - 既存コードの移行が完了していなくても、新規コードは新規約を適用する

### 記述方法

ガイドラインに以下のセクションを追加する:

```markdown
#### 既存コードへの適用

規約に準拠していない既存コードは [user-story-XXX](../../../user-stories/user-story-XXX/README.md) で対応予定。

**注意**: 新規作成時は必ず本規約に従うこと。
```

### ユーザーストーリーテンプレート

`docs/user-stories/user-story-XXX/README.md`:

```markdown
# User Story XXX: [規約名]への統一

## ストーリー

> [目的を1文で記述]

## 概要

[規約ファイルへのリンク] の「[セクション名]」規約に準拠していない既存コードを更新する。

## 対象ファイル

（別途調査）

## タスク

（別途策定）

## 受け入れ条件

（別途策定）
```

### 「適用待ちの箇所」との使い分け

| パターン | 使用場面 | 特徴 |
|---------|---------|------|
| 適用待ちの箇所 | 対象が少数・明確な場合 | ガイドライン内に詳細表を記述 |
| ユーザーストーリー連携 | 対象が多数・調査が必要な場合 | ユーザーストーリーで詳細を管理 |

どちらのパターンを使用しても、**新規作成時は必ず新しい規約に従う**点は共通である。
