# ドキュメント共通ルール

全ドキュメント種別(ADR、設計書、テスト戦略書など)に適用される共通ルール。

## 使用言語

**ドキュメントは日本語で記述すること。**

- コード例やコマンド例は英語のまま記載可
  - コードブロック（` ``` `）内のコード
  - インラインコード（`` ` ` ``）内のコード・コマンド・ファイルパス
- 技術用語は英語表記も許容（例: Clean Architecture, Repository）
- 技術用語の大文字小文字は公式表記に従うこと
  - ESLint（❌ ESlint, Eslint, eslint）
  - TypeScript（❌ Typescript, typescript）
  - JavaScript（❌ Javascript, javascript）
  - GitHub（❌ Github, github）
  - npm（❌ NPM, Npm）
- コードフェンス言語識別子は小文字を使用
  - ` ```typescript `（❌ ` ```Typescript `）
  - ` ```javascript `（❌ ` ```Javascript `）
  - これは業界標準の慣例であり、製品名の表記ルールとは別

## 文体

- 文体は断定系を使うこと
  - ですます調は使わない

## 括弧について
- 全角の括弧を使わない
  - 例: （全角） → (半角)

## コード例の記載ルール

ドキュメント種別によってコード例の扱いが異なる:

| ドキュメント種別 | コード例 | 理由 |
|----------------|---------|------|
| ADR | ❌ 記載しない | 決定と理由のみ。実装詳細は変更されやすい |
| 設計書 | ❌ 記載しない | 同上 |
| コーディング規約 | ✅ パターン例のみ | 良い例/悪い例を示すために必要 |

### ADR・設計書でのルール

- 実装コード（TypeScript、CSSなど）は変更される可能性が高く、ドキュメントとの乖離が発生しやすい
- 実装の詳細はソースコードやテストコードを参照すること

#### 既存ADRへの適用

本規約に準拠していない既存ADRは [user-story-006](../user-stories/user-story-006/README.md) で対応予定。

**注意**: 新規ADR作成時は必ず本規約に従うこと。

### コーディング規約でのコード例ルール

コーディング規約ではパターンを説明するためにコード例を記載できる。ただし以下のルールに従うこと:

- **目的**: パターンの説明（良い例/悪い例の対比）
- **範囲**: 最小限のコードで要点を示す（完全な実装ではない）
- **確認責任**: 実在するhooks/コンポーネントを参照する場合、**著者が記載時に**コードベースに存在することを確認すること

#### 「コード例」と「ソースコード参照」の使い分け

| 用途 | 方法 | 例 |
|-----|------|-----|
| パターンの説明（良い例/悪い例） | コード例を記載 | `// ❌ 悪い例` `// ✅ 良い例` |
| 完全な実装の参照 | ソースコード/テストコードへのリンク | 「詳細は[hooks/useXxx.ts]を参照」 |

**検証責任の範囲**:
- コード例内で参照するhooks/コンポーネント名 → **著者が存在確認**
- 完全な実装の詳細 → ソースコードを参照させる（ドキュメントに記載しない）

### ドキュメント例示での参照ルール

ドキュメント内で例示として何かを参照する場合、**実在するものを参照**すること。

| 参照対象 | 悪い例 | 良い例 |
|---------|-------|-------|
| ファイルパス | `path/to/file.md` | 実際のパス |
| 見出し例 | 架空の「### XXXのESLint化について」 | 実在する見出しへのリンク |
| hooks/コンポーネント | 存在しない`useXxx` | コードベースに存在するもの |

```markdown
## 悪い例（プレースホルダー/架空の例）

詳細は[コーディング規約](path/to/coding-standard.md)を参照。
見出し名にスコープを含める（例: 「### コントラスト比検証のESLint化について」）

## 良い例（実在する参照）

適用シナリオの記載例は[アクセシブルモーダルコンポーネント規約の適用シナリオ](../coding-standards/src/frameworks-and-drivers/ui/accessible-modal.md#適用シナリオ)を参照。
**実在する良い例**: [adr.md](./adr.md) の「## 悪い例（詳細を列挙）」のようにスコープを含める
```

**理由**:
- 読者が実際のパターンを確認できる
- 例示とコードベース/ドキュメントの乖離を防ぐ
- リンク切れや存在しない参照を検出できる

## 規約・ルール記述時の原則

- 規約やルールを記述する際は、具体例（シナリオ・事例）を1-2個含めること
  - 抽象的なルールだけでは実装時の判断基準が曖昧になる
  - 実際のプロジェクトで発生した事例を具体例として記載すると、チームの理解が深まる
  - **注意**: ここでいう「具体例」とは実装コードではなく、適用シナリオや判断事例を指す

**良い例**: [css-styling.md](../coding-standards/src/frameworks-and-drivers/ui/css-styling.md) の「具体例」セクションでは、デザイントークン追加時の判断フローやWCAG AA準拠のための色修正事例を記載している

### 責任の所在を明示する

ルールを記述する際、**誰が・いつ**その責任を負うかを明示すること。

```markdown
## 悪い例（責任が曖昧）

- コードベースに存在することを確認すること

## 良い例（責任が明確）

- **著者が記載時に**コードベースに存在することを確認すること
- **レビュアーがPRレビュー時に**整合性を確認すること
```

**よく使う責任パターン**:

| 責任者 | タイミング | 例 |
|-------|----------|-----|
| 著者 | 記載時 | ファイル存在確認、パス検証 |
| レビュアー | PRレビュー時 | ルール準拠の確認 |
| CI | マージ時 | 自動テスト、リンク検証 |

### 関連ルール間の関係性を明示する

同一セクション内に複数の関連ルールがある場合、**それらの関係性（使い分け・適用範囲の違い）を明示**すること。

```markdown
## 悪い例（関係性が不明確）

### ADR・設計書でのルール
- 実装の詳細はソースコードを参照すること

### コーディング規約でのコード例ルール
- 著者が記載時に存在を確認すること

## 良い例（関係性が明確）

### ADR・設計書でのルール
- 実装の詳細はソースコードを参照すること

### コーディング規約でのコード例ルール
- 著者が記載時に存在を確認すること

#### 使い分け
| 用途 | 方法 |
|-----|------|
| パターン説明 | コード例を記載 |
| 完全な実装 | ソースコードへのリンク |
```

**なぜ必要か**:
- 読者がどのルールをいつ適用すべきか判断しやすくなる
- ルール間の矛盾や曖昧さを防ぐ

## 推奨事項の理由記述

コーディング規約で特定の実装方法を推奨（または非推奨）とする場合、以下を必ず記載すること:

1. **理由（なぜその方法を推奨/非推奨とするか）**
   - 技術的な背景
   - 代替案との比較で優れている/劣っている点

2. **問題が発生するケース**（非推奨の場合）
   - 非推奨の方法を使った場合に何が起きるか
   - 具体的な環境や条件（例: テスト環境、特定のライブラリとの組み合わせ）

### 悪い例

```text
- 初期フォーカス設定（手動useEffect推奨、テスト環境との互換性のため）
```

→ 「テスト環境との互換性」だけでは、なぜ互換性の問題が生じるか不明

### 良い例

```text
- 初期フォーカス設定
  - 手動useEffectを推奨（FocusScopeのautoFocusは使用しない）
  - 理由: autoFocusはReact Ariaの内部タイミングでフォーカスを設定するため、
    テスト環境（happy-dom）でのライフサイクルと競合する可能性がある
```

→ 技術的背景と問題が発生する条件が明確

## コード内コメントの記述原則

コード内のコメント（JSDoc、インラインコメント等）にも以下の原則を適用する。

### 原則: 専門用語・抽象的な表現を避け、具体的に記述する

コメントは初めてコードを読む人が理解できる表現で記述すること。

| 避けるべき表現 | 推奨する表現 |
|---------------|-------------|
| カスケード障害を防ぐ | 他のテストケースへの影響を防ぐ |
| パフォーマンス向上のため | 不要な再レンダリングを防ぐため |
| 安全性のため | null参照エラーを防ぐため |
| 堅牢性を高める | エラー時にも正常に動作させる |

### 「なぜ」を具体的に書く

```typescript
// ❌ 悪い例: 「カスケード障害」は専門用語で意味が不明確
// カスケード障害を防ぐため早期リターン
if (!container) return;

// ✅ 良い例: 具体的な影響を記述
// setup()が呼ばれていない場合は何もせず早期リターン（他のテストケースへの影響を防ぐため）
if (!container) return;
```

### 実装詳細をコメントに含めない

将来変更される可能性のある実装詳細（具体的な値、内部形式など）をコメントに記載しない。

```typescript
// ❌ 悪い例: 実装詳細（":r0:"形式）に言及
// useIdは":r0:"のような形式のIDを生成するため、IDが存在することを確認
expect(title?.id).toBeTruthy();

// ✅ 良い例: 実装詳細を抽象化
// useIdで動的に生成されるため、IDの形式は実装依存。プレフィックス部分のみ検証する
expect(title?.id).toBeTruthy();
```

**なぜ避けるべきか**:
- 実装詳細は将来変更される可能性がある
- コメントがコードと乖離すると誤解を招く
- 「何をしているか」ではなく「なぜそうしているか」を書く

### 能力ではなく実際の動作を記述する

コメントは「何ができるか」ではなく「何をするか」を記述する。

```typescript
// ❌ 悪い例: 能力を記述（実際の動作が不明確）
// プレフィックスは確認可能
expect(id).toContain('dialog-');

// ✅ 良い例: 実際の動作を記述
// プレフィックス部分のみ検証する
expect(id).toContain('dialog-');
```

| 避けるべき（能力） | 推奨（実際の動作） |
|------------------|------------------|
| 〜は確認**可能** | 〜を**検証する** |
| 〜に対応**可能** | 〜を**処理する** |
| エラーハンドリング**可能** | エラーを**キャッチしてログ出力する** |

### チェックリスト

コメントを書く際は、以下を確認すること:

- [ ] 初めてコードを読む人が理解できる表現か
- [ ] 専門用語や業界ジャーゴンを使っていないか
- [ ] 「なぜ」が具体的に説明されているか
- [ ] 将来変更される可能性のある実装詳細（具体的な値、形式など）を含んでいないか
- [ ] 能力（〜可能）ではなく実際の動作（〜する）を記述しているか

## markdown記法
- Markdownのコードブロックに言語指定を行うこと
  - TypeScript/JavaScriptコード: `typescript`, `javascript`, `tsx`, `jsx`
  - CSSコード: `css`, `scss`
  - シェルコマンド: `bash`, `sh`
  - ディレクトリ構造: `text`
  - 設定ファイル: `json`, `yaml`
  - Markdownテンプレート: `markdown`
  - その他プレーンテキスト: `text`
- 見出しには見出し構文（`#`, `##`, `###` など）を使用すること
  - 太字強調（`**text**`）を見出しとして使用しない
  - 見出し構文を使用することで、ドキュメント構造が明確になり、目次生成やアウトライン表示がサポートされる
- 見出しレベルは階層を飛ばさないこと
  - `##` (h2) の直後に `####` (h4) を使用しない（`###` (h3) を経由する）
  - 正しい階層: `#` → `##` → `###` → `####`
  - 並列の概念は同じ見出しレベルで記述する
- 同一ドキュメント内で類似の見出し名を使う場合、スコープを明示すること
  - 同じ名前や類似の名前（例: 「eslint-rule」）を複数箇所で使うと、どのセクションがどの規約に対応するか曖昧になる
  - 見出し名にスコープを含める
  - **実在する良い例**: [adr.md](./adr.md) の「## 悪い例（詳細を列挙）」「## 良い例（参照のみ）」のようにスコープを含める

## 新規ルール追加時の原則

新しいルールをこのドキュメント（または他のdocs-rules配下）に追加する際は、以下の手順を踏むこと。

### 手順

1. 新規ルールをドキュメントに追記
2. `grep` や `Glob` で既存の違反箇所を検索
3. 以下のいずれかを選択:
   - **推奨**: 検索結果をすべて修正し、同一PRで提出
   - **代替**: 修正できない場合は「適用待ちの箇所」として記録

**例外**: `docs/completed/` 配下の履歴ドキュメントは修正対象外

詳細は [coding-standards.md](./coding-standards.md) の「新規規約追加時のルール」を参照。

## 適用待ちの箇所

規約やガイドラインを変更した際、既存のドキュメントやソースコードが新しい規約に適合していない場合がある。これらを「適用待ちの箇所」として明示的に記録する。

### 目的

- 過渡期における規約違反を可視化する
- 対応の優先度や計画を明確にする
- 新規作成時と既存修正時のルールを区別する

### 記述方法

規約を変更するドキュメントに「適用待ちの箇所」セクションを設け、以下の情報を記載する:

```markdown
## 適用待ちの箇所

### [変更内容の概要]

本規約の変更により、以下の箇所が新しい規約に適合していない:

| 対象 | 現状 | 新規約 | 備考 |
|------|------|--------|------|
| `path/to/file.ts` | 旧ディレクトリに配置 | 新ディレクトリへ移動 | 別タスクで対応 |
| `docs/design/...` | 旧フォーマット | 新フォーマットへ更新 | 優先度: 低 |

### 対応方針

- **新規作成**: 新しい規約に従う(必須)
- **既存修正**: [別タスクとして対応 / 触った際に修正 / 対応しない]
```

### 記述場所

| ドキュメント種別 | 記述場所 |
|-----------------|---------|
| ADR | 該当ADRの末尾に「適用待ちの箇所」セクションを追加 |
| コーディング規約 | 該当規約ファイルの末尾に追加 |
| 設計書ルール | `docs/docs-rules/design/` 内の該当ファイルに追加 |

### 例: ADR-004での使用

```markdown
## 適用待ちの箇所

### ドメイン層に誤って配置された Tab 関連クラス

本 ADR の決定により、以下のファイルが新しい規約に適合していない:

| 対象 | 現状 | 新規約 | 備考 |
|------|------|--------|------|
| `Tab.ts` | `src/domain/value-objects/` | `src/frameworks-and-drivers/browser/` | 別タスクで対応 |
| `Tabs.ts` | `src/domain/value-objects/` | `src/frameworks-and-drivers/browser/` | 別タスクで対応 |

### 対応方針

- **新規作成**: 新しい規約に従う(必須)
- **既存修正**: 本ユーザーストーリーのスコープ外、別途リファクタリングタスクとして実施
```

### 注意事項

- 「適用待ちの箇所」は規約違反ではなく、**計画的な移行待ち状態**である
- 新規作成時は必ず新しい規約に従うこと
- 対応完了後は該当項目を削除またはチェック済みに更新すること

## ガイドライン更新時のユーザーストーリー連携

ガイドライン(コーディング規約、テスト規約など)を更新した際、既存のコードやドキュメントとの不整合が発生する場合がある。この不整合解消は、別途ユーザーストーリーを新規作成して対応する。

### 原則

1. **ガイドラインにはユーザーストーリーへのリンクのみ表示する**
   - 不整合箇所の詳細（どのファイルが違反しているか等）はガイドラインに記述しない
   - ユーザーストーリー内で詳細を管理する

2. **ガイドライン更新PRでは、ユーザーストーリーはテンプレートのみ作成する**
   - 対象ファイル、タスク、受け入れ条件は「（別途調査）」「（別途策定）」とする
   - ユーザーストーリーの詳細策定は別途PRで対応する

3. **新規作成時は必ず新しい規約に従う**
   - 既存コードの移行が完了していなくても、新規コードは新規約を適用する

### 記述方法

ガイドラインに以下のセクションを追加する:

```markdown
#### 既存コードへの適用

規約に準拠していない既存コードは [user-story-XXX](../../../user-stories/user-story-XXX/README.md) で対応予定。

**注意**: 新規作成時は必ず本規約に従うこと。
```

### ユーザーストーリーテンプレート

`docs/user-stories/user-story-XXX/README.md`:

```markdown
# User Story XXX: [規約名]への統一

## ストーリー

> [目的を1文で記述]

## 概要

[規約ファイルへのリンク] の「[セクション名]」規約に準拠していない既存コードを更新する。

## 対象ファイル

（別途調査）

## タスク

（別途策定）

## 受け入れ条件

（別途策定）
```

### 「適用待ちの箇所」との使い分け

| パターン | 使用場面 | 特徴 |
|---------|---------|------|
| 適用待ちの箇所 | 対象が少数・明確な場合 | ガイドライン内に詳細表を記述 |
| ユーザーストーリー連携 | 対象が多数・調査が必要な場合 | ユーザーストーリーで詳細を管理 |

どちらのパターンを使用しても、**新規作成時は必ず新しい規約に従う**点は共通である。
