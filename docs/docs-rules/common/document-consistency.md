# ドキュメント整合性

## 関連ドキュメント間の一貫性

同一ディレクトリ内や関連するドキュメント群を作成・編集する際は、**構造とセクションの一貫性を維持**すること。

### 適用場面

- 1つのドキュメントを複数ファイルに分割する場合
- 同一カテゴリの複数ドキュメントを作成する場合
- 既存の関連ドキュメント群に新規ファイルを追加する場合

### ルール

1. **同一ディレクトリ内のドキュメントは同じ構造を持つこと**
   - 共通セクション（例: 「ESLint化について」）は全ファイルに含める
   - リンク先（例: 関連するユーザーストーリー）も統一する

2. **分割時のチェックリスト**
   - 分割後の全ファイルに必要なセクションが含まれているか確認
   - 元ファイルにあった参照リンクが全ファイルに適切に配置されているか確認

3. **外部からの参照更新（必須）**
   - ドキュメントを分割・移動・リネームした場合、**著者が記載時に**他ドキュメントからの参照を検索し更新すること
   - 検索コマンド例: `grep -r "旧ファイル名" docs/`
   - 同一PRで参照元も更新する（リンク切れを防ぐ）

### 具体例

（※説明用の形式例 - 不整合パターンの例示）
```text
feature-docs/
├── index.md              # 概要
├── setup.md              # → 関連Issue 123へのリンクあり
├── configuration.md      # → 関連Issue 123へのリンクあり
├── troubleshooting.md    # → 関連Issue 123へのリンクなし ← 不整合！
└── faq.md                # → 関連Issue 123へのリンクあり
```

上記のような不整合を防ぐため、関連ドキュメントを作成・編集する際は、同一ディレクトリ内の他ファイルを確認すること。

## ドキュメント内整合性チェック

同一ドキュメント内で同じ対象(ファイル名、パス、数値など)を複数箇所で言及する場合、以下を確認すること。

### チェックリスト

- [ ] 図・表・リストで言及した名前が、他のセクションでも同じ名前で統一されているか
- [ ] 「〜案」「検討中」などの提案事項を含める場合、採否と作業手順への反映方針を明記しているか
- [ ] 作業手順には確定事項のみ記載し、未確定の提案は別途「検討事項」セクションに分離しているか
- [ ] 一箇所を修正した場合、同じ情報を記載している他の箇所も更新したか
- [ ] 記号(→、←など)の前後のスペースが統一されているか
- [ ] 同じ意味の用語が統一されているか(例: 「Content Script」と「Content」の混在を避ける)

### 関連箇所の同時更新ルール

ドキュメント内で同じ情報を複数箇所に記載している場合(表と図、概要と詳細など):

1. **一方を修正したら、関連する他の箇所も確認・更新すること**
2. **特に「概要→詳細」「表→図」のような構造では整合性を確認**

| よくある修正漏れパターン | 対策 |
|------------------------|------|
| 「移管対象ファイル」表の移管先と「移管後のディレクトリ構成」図が不一致 | 図を修正したら表も確認 |
| 概要セクションの説明と詳細セクションの内容が矛盾 | 詳細を修正したら概要も確認 |
| 目次と実際の見出しが不一致 | 見出しを変更したら目次も更新 |

### 提案事項の記述ルール

ドキュメント内で「〜案」「検討中」「候補」などの提案事項を記載する場合:

1. **採否を明示する**: 提案が確定か未確定かを明記
   - 確定: 「(採用予定)」「→ 〜に変更」
   - 未確定: 「(要検討)」「(別途決定)」

2. **作業手順には確定事項のみ記載**: 提案が未確定の場合、作業手順には現状の名前を使用

| 悪い例 | 良い例 |
|-------|-------|
| `newName.ts(名称変更案)` | `newName.ts(採用予定)` または `oldName.ts(名称変更は要検討)` |

### 具体例

```markdown
## 悪い例(名称の不整合)

### 移管後の構成
- onBackgroundMessageReceived.ts(名称変更案)

### 必要な作業
- onMessageReceived.ts を移動  ← 図と不一致、採否も不明確

## 良い例(整合性あり)

### 移管後の構成
- onMessageReceived.ts(名称変更は別タスクで検討)

### 必要な作業
- onMessageReceived.ts を移動  ← 図と一致
```

### よくある不整合パターン

| パターン | 問題 | 対策 |
|---------|------|------|
| 図では名称変更後、手順では変更前 | 実装時に混乱 | どちらかに統一、または両方記載 |
| 「5ファイル移動」と書いて4ファイルしかリストにない | 漏れの発見が困難 | リスト作成後に数を数える |
| 提案事項の採否が不明確 | 作業時に判断できない | 「(採用予定)」「(要検討)」を明記 |
| 本文では `A → B`、表では `A→B` | 読みづらく統一感がない | 記号の前後スペースを統一 |
| 本文では「Content Script」、表では「Content」 | 同じものか判断しづらい | 用語を統一 |

## ディレクトリ構成図のルール

ディレクトリ構成図を記載する際は、以下を確認すること:

### チェックリスト

- [ ] 同一ディレクトリに同名ファイルが存在しないか(ファイルシステム上不可能)
- [ ] 図に記載した構成がファイルシステムとして実現可能か
- [ ] 移管元で別ディレクトリにあったファイルの移管先配置が明確か

### 具体例

```text
## 悪い例(同名ファイルが同一階層に存在)

src/messaging/
├── onMessageReceived.ts  （background用）
├── onMessageReceived.ts  （content用）  ← ファイルシステム上不可能
└── messaging.ts

## 良い例(サブディレクトリで分離)

src/messaging/
├── background/
│   └── onMessageReceived.ts
├── content/
│   └── onMessageReceived.ts
└── messaging.ts
```

**注意**: 移管元で別ディレクトリにあったファイルを同一ディレクトリに集約する場合、名称衝突の可能性を確認すること。

## 図の時点（状態）を明示するルール

移管・リファクタリング計画のドキュメントで図を記載する場合:

1. **図がどの時点の状態かを見出しで明示する**
   - 現在の状態: 「現在の依存関係」「移管前の構成」
   - 変更後の状態: 「移管後のディレクトリ構成」

2. **同一ドキュメント内で複数時点の図がある場合、それぞれにラベルを付ける**

| 悪い例 | 良い例 |
|-------|-------|
| `#### 依存関係` | `#### 依存関係（現在・移管前）` |
| `#### ディレクトリ構成` | `#### 移管後のディレクトリ構成` |

**理由**: 移管計画では「現在」と「移管後」の両方の図が必要になることが多い。時点を明示しないと、読者がどちらの状態を示しているか判断できない。
