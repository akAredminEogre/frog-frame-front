# 規約・ルール記述時の原則

## リストと数値の整合性

リストを列挙する際に項目数を明示する場合、以下のルールに従うこと。

**ルール**:
- テーブルの行数やリスト項目数を数えて記載する場合、追記・削除時に数値も更新すること
- PR説明文で数値を使う場合、本文の項目数と一致させること

**推奨**: 変動しやすいリストでは項目数を明示しない

```markdown
## 悪い例（数値の不整合リスク）

### 対象ファイル（3ファイル）
- file1.md
- file2.md
- file3.md
- file4.md  ← 追加時に見出しの数値を更新し忘れる

## 良い例（数値を明示しない）

### 対象ファイル
- file1.md
- file2.md
- file3.md
- file4.md
```

**例外**: 数値が重要な意味を持つ場合（例: 「9つのルール」のような固有名詞）は明示してよい。

## 具体例の記載

- 規約やルールを記述する際は、具体例（シナリオ・事例）を1-2個含めること
  - 抽象的なルールだけでは実装時の判断基準が曖昧になる
  - 実際のプロジェクトで発生した事例を具体例として記載すると、チームの理解が深まる
  - **注意**: ここでいう「具体例」とは実装コードではなく、適用シナリオや判断事例を指す

**良い例**: [design-tokens.md](../../coding-standards/src/frameworks-and-drivers/ui/css-styling/design-tokens.md) の「具体例」セクションでは、削除ボタン用トークンの選定手順やWCAG AA準拠のための色修正事例を記載している

## 良い例/悪い例の対比は1つの差分のみ

「良い例」と「悪い例」を対比させる際は、**差分を1つに限定**すること。複数の差分があると、どの点が修正ポイントか不明確になる。

**避けるべき対比（悪い書き方）**:

以下は2つの差分（数値と検証ツール記載）があり、どちらが修正ポイントか不明確な例:

```text
悪い例: /* コントラスト比: 約4.58:1 */
良い例: /* コントラスト比: 約4.52:1 (WebAIM Contrast Checkerで確認) */
→ 問題: 数値も変わり、検証ツールも追加。どちらが本質的な修正？
```

**推奨する対比（良い書き方）**:

以下は1つの差分（検証ツール記載の有無）のみで、修正ポイントが明確な例:

```text
悪い例: /* コントラスト比: 約4.52:1 */
良い例: /* コントラスト比: 約4.52:1 (WebAIM Contrast Checkerで確認) */
→ 明確: 検証ツール記載の追加が修正ポイント
```

## ディレクトリ・ファイル構成例の実在性明示

ドキュメント内でディレクトリ構成やファイル一覧を例示する際は、**著者が記載時に**それが実在するものか形式例かを明示すること。

```markdown
## 悪い例（実在性が不明）

feature-docs/
├── index.md
├── setup.md
└── usage.md

## 良い例（実在構成であることを明示 - 全ファイル記載）

（※実在するディレクトリ構成）
css-styling/
├── index.md
├── import-paths.md
├── design-tokens.md
├── color-contrast.md
└── touch-target-size.md

## 良い例（実在構成の一部を抜粋）

（※実在するディレクトリ構成より抜粋）
src/components/
├── atoms/
│   └── ...（他のコンポーネント）
└── molecules/

## 良い例（形式例であることを明示）

（※説明用の形式例）
feature-name/
├── index.md
├── overview.md
└── details.md
```

**理由**: 読者が例示を見たとき、実際のファイルを確認すべきか判断できるようにするため。

**注意**: 実在構成を示す場合は、全ファイルを記載するか「抜粋」であることを明示すること。

## 実在例の同期更新

実在するファイルやディレクトリを「悪い例」として使用した場合、その状態を修正したら**著者が同一PRで**例示も更新すること。

```markdown
## 問題のあるパターン

1. 実在する不整合を「悪い例」として記載
2. 同じPRでその不整合を修正
3. 例示の更新を忘れる → 例示と実態が乖離

## 推奨パターン

- **形式例を使う**: 実在しない架空のディレクトリ名で「悪い例」を示す
- **同期更新する**: 実在例を使う場合は、修正時に例示も更新する
```

## 責任の所在を明示する

ルールを記述する際、**誰が・いつ**その責任を負うかを明示すること。

```markdown
## 悪い例（責任が曖昧）

- コードベースに存在することを確認すること

## 良い例（責任が明確）

- **著者が記載時に**コードベースに存在することを確認すること
- **レビュアーがPRレビュー時に**整合性を確認すること
```

**よく使う責任パターン**:

| 責任者 | タイミング | 例 |
|-------|----------|-----|
| 著者 | 記載時 | ファイル存在確認、パス検証 |
| レビュアー | PRレビュー時 | ルール準拠の確認 |
| CI | マージ時 | 自動テスト |

## 新セクション追加時の既存原則チェック

ドキュメントに新しいセクションやルールを追加する際、**著者が記載時に**同一ドキュメント内の既存原則を確認し、それらに準拠すること。

**チェック項目**:
- 責任の所在（誰が・いつ）が明示されているか
- 関連する既存ルールとの整合性があるか
- 具体例が必要な場合は記載されているか

```markdown
## 悪い例（既存原則を無視）

3. **外部からの参照更新（必須）**
   - ドキュメントを分割した場合、他ドキュメントからの参照を更新すること
   <!-- 責任者・タイミングが不明確 -->

## 良い例（既存原則に準拠）

3. **外部からの参照更新（必須）**
   - ドキュメントを分割した場合、**著者が記載時に**他ドキュメントからの参照を更新すること
```

## 関連ルール間の関係性を明示する

同一セクション内に複数の関連ルールがある場合、**それらの関係性（使い分け・適用範囲の違い）を明示**すること。

```markdown
## 悪い例（関係性が不明確）

### ADR・設計書でのルール
- 実装の詳細はソースコードを参照すること

### コーディング規約でのコード例ルール
- 著者が記載時に存在を確認すること

## 良い例（関係性が明確）

### ADR・設計書でのルール
- 実装の詳細はソースコードを参照すること

### コーディング規約でのコード例ルール
- 著者が記載時に存在を確認すること

#### 使い分け
| 用途 | 方法 |
|-----|------|
| パターン説明 | コード例を記載 |
| 完全な実装 | ソースコードへのリンク |
```

**なぜ必要か**:
- 読者がどのルールをいつ適用すべきか判断しやすくなる
- ルール間の矛盾や曖昧さを防ぐ
