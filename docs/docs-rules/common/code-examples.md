# コード例の記載ルール

## ドキュメント種別による扱い

ドキュメント種別によってコード例の扱いが異なる:

| ドキュメント種別 | コード例 | 理由 |
|----------------|---------|------|
| ADR | ❌ 記載しない | 決定と理由のみ。実装詳細は変更されやすい |
| 設計書 | ❌ 記載しない | 同上 |
| コーディング規約 | ✅ パターン例のみ | 良い例/悪い例を示すために必要 |

## ADR・設計書でのルール

- 実装コード（TypeScript、CSSなど）は変更される可能性が高く、ドキュメントとの乖離が発生しやすい
- 実装の詳細はソースコードやテストコードを参照すること

### 既存ADRへの適用

本規約に準拠していない既存ADRは [user-story-006](../../user-stories/completed/user-story-006/README.md) で対応済み。

**注意**: 新規ADR作成時は必ず本規約に従うこと。

## コーディング規約でのコード例ルール

コーディング規約ではパターンを説明するためにコード例を記載できる。ただし以下のルールに従うこと:

- **目的**: パターンの説明（良い例/悪い例の対比）
- **範囲**: 最小限のコードで要点を示す（完全な実装ではない）
- **確認責任**: 実在するhooks/コンポーネントを参照する場合、**著者が記載時に**コードベースに存在することを確認すること

### 「コード例」と「ソースコード参照」の使い分け

| 用途 | 方法 | 例（形式のみ） |
|-----|------|-----|
| パターンの説明（良い例/悪い例） | コード例を記載 | `// ❌ 悪い例` `// ✅ 良い例` |
| 完全な実装の参照 | ソースコード/テストコードへのリンク | 「詳細は[実在パス]を参照」 |

**検証責任の範囲**:
- コード例内で参照するhooks/コンポーネント名 → **著者が存在確認**
- 完全な実装の詳細 → ソースコードを参照させる（ドキュメントに記載しない）

## ドキュメント例示での参照ルール

ドキュメント内で例示として何かを参照する場合、**実在するものを参照**すること。

**自己矛盾の回避**: このルールを記述するドキュメント自身も、このルールに従うこと。形式のみを示す例（パターン例）の場合は、列見出しに「形式のみ」等を明記するか、`[実在パス]`のように明らかなプレースホルダーを使用する。

| 参照対象 | 悪い例 | 良い例 |
|---------|-------|-------|
| ファイルパス | `path/to/file.md` | 実際のパス |
| 見出し例 | 架空の「### XXXのESLint化について」 | 実在する見出しへのリンク |
| hooks/コンポーネント | 存在しない`useXxx` | コードベースに存在するもの |

```markdown
## 悪い例（プレースホルダー/架空の例）

詳細は[コーディング規約](path/to/coding-standard.md)を参照。
見出し名にスコープを含める（例: 「### コントラスト比検証のESLint化について」）

## 良い例（実在する参照）

適用シナリオの記載例は[アクセシブルモーダルコンポーネント規約の適用シナリオ](../../coding-standards/src/frameworks-and-drivers/ui/accessible-modal.md#適用シナリオ)を参照。
**実在する良い例**: [adr.md](../adr.md) の「## 悪い例（詳細を列挙）」のようにスコープを含める
```

**理由**:
- 読者が実際のパターンを確認できる
- 例示とコードベース/ドキュメントの乖離を防ぐ
- リンク切れや存在しない参照を検出できる

**参照の具体性**:
- 「詳細は〇〇を参照」のような曖昧な参照を避ける
- 参照先の**具体的なセクション名**を明示する（例: `#適用シナリオ`）
- 参照の目的（何を確認すべきか）を明記する

**参照説明の正確性**:

他ドキュメントを参照する際、その内容を説明する場合は**著者が記載時に**参照先を確認し、説明が実際の内容と一致することを検証すること。

```markdown
## 悪い例（説明が実態と異なる）

[design-tokens.md]の「具体例」セクションでは、判断フローを記載している
<!-- 実際には「手順」であり「判断フロー」という形式ではない -->

## 良い例（説明が実態と一致）

[design-tokens.md]の「具体例」セクションでは、トークン選定手順を記載している
```

**ドキュメント形式用語の正確な使い分け**:

ドキュメントの構造・形式を説明する際は、**実際の形式に対応する用語**を使用すること。形式用語には明確な意味の違いがあり、誤用すると読者に誤解を与える。

| 形式用語 | 意味 | 実際のドキュメント構造 |
|---------|------|---------------------|
| 判断フロー | 条件分岐のある決定木 | 「〜の場合は A、そうでなければ B」のような分岐構造 |
| 手順 | 順序付きステップ | 「1. 〜する 2. 〜する」のような番号付きリスト |
| チェックリスト | 確認項目の一覧 | `- [ ]` 形式のタスクリスト |
| ガイドライン | 推奨事項・方針 | 「〜すること」「〜を推奨」のような記述 |
| 事例 | 具体的な実例 | 実際に発生した状況とその対応の記述 |

**チェックポイント**: 参照先を「〜フロー」「〜手順」等と説明する場合、参照先の実際の構造（番号付きリスト？分岐？チェックボックス？）を確認してから用語を選択すること。

## ファイルパス参照時のチェックリスト

ドキュメント内でファイルパスを記載する際は、以下を確認すること:

- [ ] 記載したパスが実在することを確認したか（`ls`やGlobで検証）
- [ ] 相対パスの基準ディレクトリを意識しているか（ドキュメントの配置場所からの相対パス）
- [ ] 省略形ではなく完全なパスを記載しているか

**よくある間違い**:

| 間違い | 正しいパス |
|-------|-----------|
| `src/coding-standards.md` | `docs/coding-standards/src/coding-standards.md` |
| `tests/common-rule.md` | `docs/coding-standards/tests/common-rule.md` |

## 例示のフォーマット一貫性

同一ドキュメント内で例を記載する際は、そのドキュメントで定義したフォーマットルールに従うこと。

```markdown
## 悪い例（ドキュメント内で定義したルールと例が不一致）

基本ルールで「AC-1, AC-2... のようにAC番号を付ける」と定義しているのに:

- [ ] 対象ファイルすべてに適用シナリオが追加されている  ← AC番号なし

## 良い例（ドキュメント内のルールと例が一致）

- [ ] AC-1: 対象ファイルすべてに適用シナリオが追加されている  ← AC番号あり
```
