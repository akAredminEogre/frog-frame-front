# 07-e2e-test-strategy.md ルール

E2Eテストの設計意図と網羅性を可視化するドキュメント。

## 目的

- ユーザー視点での機能動作を検証する設計を明文化
- UIからDB永続化までのエンドツーエンドのフローを可視化
- テスト環境（Playwright、ローカルHTTPサーバー等）の構成を明確化
- ユーザーストーリーとの対応関係を定義

## 他のテストとの違い

| 観点 | 単体テスト | 結合テスト | E2Eテスト |
|------|-----------|-----------|----------|
| **スコープ** | 1クラス/1メソッド | 複数レイヤーのフロー | UI操作からDB永続化まで |
| **配置基準** | ソースコード構造に対応 | feature単位 | feature単位 |
| **実行環境** | Vitest（Node.js） | Vitest + fake-indexeddb | Playwright + 実ブラウザ |
| **モック戦略** | 依存を全てモック | 外部依存のみモック | 原則モックなし |
| **検証対象** | 入出力の正確性 | レイヤー間の連携 | ユーザー体験 |
| **DB** | モック | 実DB（fake-indexeddb） | 実DB（IndexedDB） |

## 配置

E2Eテスト戦略書は、featureの `00-overview.md` と同じディレクトリに配置する。

```
docs/design/pages/{page-name}/features/{feature-name}/
├── 00-overview.md
├── integration-test-strategy.md
└── e2e-test-strategy.md    # ← ここに配置
```

### 配置例

| feature | テスト戦略書 |
|---------|-------------|
| toggle-rule-active（ルール有効/無効切り替え） | `docs/design/pages/rule-list/features/toggle-rule-active/e2e-test-strategy.md` |
| create-rule（ルール作成） | `docs/design/pages/popup/features/create-rule/e2e-test-strategy.md` |

### 設計意図

- **feature単位**: ユーザーストーリーに対応したテスト管理
- **設計ドキュメントと同一ディレクトリ**: 機能要件との対応を明確化
- **結合テストとの対比**: 同じfeatureに対する異なるレベルのテストを並置

## テストスコープの定義

### 対象フローの記述

ユーザー操作の流れをステップで示す:

```markdown
### 対象フロー

1. ユーザーがルール一覧ページを開く
2. トグルスイッチをクリック
3. ルールの有効/無効が切り替わる
4. ページをリロードしても状態が維持される

### 対象ページ

| ページ | URL | 役割 |
|-------|-----|------|
| ルール一覧 | `chrome-extension://{id}/rules.html` | トグル操作 |
| ポップアップ | `chrome-extension://{id}/popup.html` | ルール作成 |
| テストページ | `http://localhost:8080/test.html` | DOM置換検証 |
```

### 検証ポイント

E2Eテスト特有の検証観点:

| 観点 | 説明 | 例 |
|------|------|-----|
| UI状態変化 | 操作後のUI表示 | トグルがON→OFF |
| DB永続化 | リロード後も状態維持 | ページリロードで確認 |
| コンソールエラー | エラーが発生しないこと | `console.error` 監視 |
| ダイアログ表示 | アラート/確認ダイアログ | 保存完了メッセージ |

## テスト分類の観点

E2Eテスト特有の観点:

| 観点 | 説明 | 例 |
|------|------|-----|
| 正常操作フロー | 基本的なユーザー操作 | トグルクリック→状態変化 |
| 状態永続化 | リロード後の状態維持 | DB保存の検証 |
| 複数データ操作 | 複数アイテムの独立性 | 他ルールへの影響なし |
| エラー表示 | エラー時のUI表示 | エラーメッセージ表示 |
| 競合防止 | 連続操作の制御 | 処理中の操作ブロック |

## 記述ルール

### ユーザー操作の記述

ユーザー視点での操作を具体的に記述:

```markdown
### 対象フロー

1. ユーザーがポップアップを開く
2. 置換前/置換後の文字列を入力
3. 「保存」ボタンをクリック
4. 「保存して適用しました！」ダイアログが表示される
5. ルール一覧ページで保存されたルールが表示される
```

### 検証ポイントの明確化

何を検証するかを具体的に記述:

```markdown
### 検証ポイント

| 観点 | 検証内容 | セレクタ/API |
|------|---------|-------------|
| トグル状態 | data-selected属性がtrue/false | `[data-selected]` |
| ルール数 | フッターの表示 | `text=合計 N 件` |
| コンソールエラー | エラーログなし | `page.on('console')` |
```

### ダイアログ処理の注意点

Playwrightでのダイアログ処理には注意が必要:

```typescript
// 推奨: waitForEventを使用
const [dialog] = await Promise.all([
  page.waitForEvent('dialog', { timeout: 60000 }),
  saveButton.click(),
]);
expect(dialog.message()).toBe('保存しました！');
await dialog.accept();

// 非推奨: page.on('dialog')の複数登録
// 複数回呼び出すと重複登録される問題がある
```

### コンソールエラー監視

E2Eテストでは必ずコンソールエラーを監視:

```typescript
const consoleMessages: string[] = [];

page.on('console', msg => {
  if (msg.type() === 'error') {
    consoleMessages.push(msg.text());
  }
});

// テスト終了時に検証
expect(consoleMessages).toHaveLength(0);
```

## テストファイル命名規則

| ファイル名 | 内容 |
|-----------|------|
| `{feature-name}.spec.ts` | E2Eテスト本体 |
| `fixtures.ts` | テストフィクスチャ（context, extensionId等） |
| `config.ts` | テスト設定（拡張機能ディレクトリ等） |
| `test-pages/*.html` | テスト用HTMLページ |

## 実行環境

- **テストフレームワーク**: Playwright
- **ブラウザ**: Chromium（Chrome拡張機能対応）
- **テストページサーバー**: ローカルHTTPサーバー（localhost:8080）
- **拡張機能**: ビルド済みの拡張機能をロード

## 結合テストとの関係

| 結合テスト | E2Eテスト |
|-----------|----------|
| Factory→Controller→UseCase→DB | UI→拡張機能全体→DB |
| モック: Chrome API | モック: なし（実環境） |
| 高速（Vitest） | 低速（実ブラウザ） |
| 詳細なエラー検出 | ユーザー体験の検証 |

両方のテストを組み合わせることで、信頼性を担保する:

1. **結合テスト**: ロジックの正確性を高速に検証
2. **E2Eテスト**: 実環境でのユーザー体験を検証
